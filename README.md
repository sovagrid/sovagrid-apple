# SovaGrid для iPhone, iPad и Mac

Нативный SSH-клиент с вкладками терминала, файлов, мониторинга Hub, полной Web-панели через SSH и настроек.

Во вкладке «Настройки» можно выбрать оформление «Как на устройстве», «Светлая» или «Тёмная». Выбор сохраняется между запусками и сразу применяется к нативным экранам и цветам SSH-терминала. Встроенная веб-панель также предлагает собственный выбор темы.

## Запуск

1. Откройте `SovaGrid.xcodeproj` в Xcode 27.1 или новее.
2. Выберите схему `SovaGrid` для iPhone/iPad или `SovaGridMac` для macOS.
3. Xcode загрузит Swift Package Dependencies по `Package.resolved`.
4. Для физического устройства выберите свою команду Apple Development в Signing & Capabilities и замените bundle identifier, если `com.sovagrid.app` / `com.sovagrid.mac` уже заняты.

Проверенные команды сборки:

```sh
xcodebuild -project SovaGrid.xcodeproj -scheme SovaGrid -configuration Debug -destination 'generic/platform=iOS' CODE_SIGNING_ALLOWED=NO build
xcodebuild -project SovaGrid.xcodeproj -scheme SovaGridMac -configuration Debug -destination 'generic/platform=macOS' CODE_SIGNING_ALLOWED=NO build
```

Для проверки сгенерированных SSH-ключей **в iPhone Simulator** установите сборку с подписью: при `CODE_SIGNING_ALLOWED=NO` симулятор возвращает ошибку Keychain `-34018` при сохранении ключа. Подходит ad hoc подпись `CODE_SIGNING_ALLOWED=YES CODE_SIGN_IDENTITY=-`.

## SSH-терминал

- Профиль содержит адрес, порт, имя пользователя и вход по SSH-паролю или ключу Ed25519. Для нового ключа нажмите «Создать ключ и показать открытый ключ» прямо в форме профиля: открытый ключ появится здесь же до сохранения. Его можно скопировать в раздел SSH-ключей хостинга либо скопировать готовую команду добавления в `~/.ssh/authorized_keys` для запуска под нужным пользователем сервера. Сохранение профиля без выбора или создания ключа не создаёт скрытый ключ. Для импорта откройте существующий приватный ключ OpenSSH через системный выбор файла. Для конечного и промежуточного сервера ключи выбираются независимо.
- Необязательный промежуточный SSH-сервер (ProxyJump) имеет **свои** адрес, порт, имя пользователя и способ входа. Приложение открывает `direct-tcpip` на нём, затем устанавливает второе SSH-соединение до сервера назначения. Для каждого узла отдельно проверяется и закрепляется `SHA256` отпечаток ключа сервера.
- После входа создаётся интерактивная shell-сессия. Размер PTY следует за размером SwiftTerm, поэтому приглашение и вывод команд отображаются без наложений.
- При уходе с экрана или переводе приложения в фон SSH-сессия закрывается. После возвращения на экран её можно запустить кнопкой «Подключить».

Пример доступа к целевому серверу через обратный SSH-туннель на промежуточном узле:

| Поле | Значение |
| --- | --- |
| Сервер назначения | `127.0.0.1:<порт-туннеля>`, пользователь целевого сервера |
| Промежуточный сервер | Публичный адрес, SSH-порт и пользователь промежуточного узла |

Адрес назначения разрешается **на промежуточном узле**. Обратный туннель поднимает целевой сервер; приложение использует уже доступный порт.


Импорт принимает незашифрованный приватный ключ формата `OPENSSH PRIVATE KEY` с алгоритмом Ed25519, до 64 КиБ. Приложение проверяет структуру, контрольные числа и padding, а также совпадение обоих открытых ключей и открытой части, вычисленной из приватного seed. В Keychain сохраняется только 32-байтный seed; исходный файл не копируется в папку приложения. Зашифрованные ключи и другие алгоритмы получают понятную ошибку. Импорт не изменяет сервер: соответствующий открытый ключ должен быть уже разрешён в `authorized_keys`.

После ухода формы в фон введённые пароли и выбранные приватные ключи очищаются. Режим «Импортировать» остаётся выбранным и требует выбрать файл снова: приложение не подменяет импорт новым случайным ключом. Существующий файл ключа в вашем хранилище остаётся на месте.

## Создать SSH-ключ и скопировать открытую часть

Откройте **SSH → SSH-ключи**, задайте название и нажмите **Создать ключ**. Приложение сразу покажет открытый ключ и кнопку **Скопировать открытый ключ**. Подключаться к серверу или заполнять профиль для этого не нужно. [Экран копирования](screenshots/ios-generated-public-key.png) показывает только публичную часть.

Создаётся стандартная пара Ed25519. Приватный seed хранится только в Keychain `WhenUnlockedThisDeviceOnly`; в настройках приложения сохраняются название, UUID и дата. В буфер обмена попадает одна строка `ssh-ed25519 …`, пригодная для вставки в настройки SSH на сервере. Приватная часть в этом интерфейсе не отображается и не экспортируется.

Чтобы использовать пару, в профиле выберите **Ключ Ed25519 → Мои ключи**. Для конечного сервера и ProxyJump можно выбрать разные ключи. В форме профиля также доступны кнопки **Создать ключ** и **Создать ключ перехода**, после которых открытую часть можно скопировать сразу. Профиль сохраняет собственную копию выбранного seed в Keychain; удаление ключа из библиотеки не ломает сохранённые подключения. Диалог удаления объясняет это и напоминает, что отзыв доступа выполняется удалением открытого ключа на сервере.

`python3 tests/integration/run_key_generation.py --app <Simulator.app>` создаёт чистый Simulator и проверяет две разные пары, их публичные части системным `ssh-keygen`, содержимое системного буфера, восстановление после перезапуска и независимый выбор target/ProxyJump. В файлах настроек проверяется отсутствие приватных ключей. После теста созданный Simulator удаляется.

## Файлы через SFTP

На вкладке **Файлы** выберите сохранённый SSH-профиль. Откройте нужную папку, коснитесь файла для скачивания либо выберите локальный файл кнопкой **Загрузить файл**. Скачанный файл сохраняется системным диалогом в выбранном месте. Профиль с ProxyJump устанавливает второе SSH-соединение до сервера назначения; для обоих узлов отдельно используются сохранённые учётные данные и закреплённые host keys. Пароли, ключи и пути не передаются в shell-команды.

Передача использует подсистему SFTP версии 3 поверх SwiftNIO SSH. Приложение отправляет и читает блоки по 32 КиБ, допускает файлы до 128 МиБ и списки до 1000 объектов. Загрузка создаёт файл с правами `0600` через `CREATE|EXCL`: существующий файл не перезаписывается. Успех показывается после подтверждения `CLOSE` сервером. При ошибке приложение пытается удалить неполный файл; если соединение оборвалось или удаление не удалось, неполный файл может остаться на сервере. Кнопка отмены закрывает соединение и предупреждает об этом риске. Скачивание использует временную папку `0700` и файл `0600`, которые удаляются после сохранения, отмены или ошибки; после принудительной остановки приложения оставшиеся временные папки удаляются при следующем запуске. Символические ссылки и специальные файлы не открываются как обычные файлы; для них используйте терминал.

SwiftNIO SSH предоставляет SSH-каналы и запрос подсистемы, но не готовый SFTP-клиент. Используемый ограниченный клиент следует [описанию SFTP v3](https://datatracker.ietf.org/doc/html/draft-ietf-secsh-filexfer-02) и [API SwiftNIO SSH](https://github.com/apple/swift-nio-ssh/blob/main/README.md). Сервер должен разрешать подсистему `sftp`.

## Полная панель Hub через SSH

Перед загрузкой панели приложение читает состояние выбранного узла по уже проверенному SSH-соединению. Оно различает управляемый Hub, отдельный Agent, чистый Ubuntu-сервер, конфликтующие файлы и неподдерживаемую ОС. «Чистый сервер» подтверждается только при входе root или через `sudo -n`; неопределённый ответ не разрешает установку и не мешает попытке открыть уже работающую панель. Для чистого сервера при входе `root` приложение предлагает установку прямо с iPhone, iPad или Mac после отдельного подтверждения. Сервер загружает ровно пакет релиза `server-v0.11.0` по HTTPS, сверяет встроенный SHA-256 пакета и манифеста, повторяет проверку пустого Ubuntu-сервера и запускает `run.sh`. Ход установки виден на экране. Установка работает как отдельное задание systemd: при уходе приложения в фон она продолжается на сервере, а после нового SSH-входа приложение читает закрытое состояние и возвращается к прогрессу. После подтверждения установленного Hub панель открывается через SSH-туннель. Серверу требуется доступ к GitHub и одна из программ `curl`, `wget` или `python3`; при отсутствии доступа подготовьте пакет по инструкции Blueprint и установите его с доверенного компьютера. Вход через `sudo -n` подходит для чтения состояния, но установка с устройства требует `root`. Если серверная установка завершится с ошибкой, её состояние сохранится; приложение не повторит её поверх существующих файлов. Сначала проверьте сервер. Узел с отдельным Agent не перезаписывается: существующие ключи и обратный SSH-туннель остаются на месте. На управляемом Hub root или `sudo -n` получают одноразовый SSH-грант; кнопка «Войти через SSH» позволяет повторить вход в текущем соединении, если первая попытка не удалась. Грант передаётся только в JavaScript текущей локальной панели и погашается POST-запросом. В URL, Keychain и UserDefaults грант не записывается; старый Hub оставляет обычную форму входа.

На вкладке **Панель** выберите SSH-профиль и узел, на котором установлен Hub. У профиля с ProxyJump можно открыть Hub на промежуточном либо на конечном узле. Второй вариант устанавливает отдельное SSH-соединение через промежуточный узел. Без ProxyJump панель открывается на единственном сервере профиля. В каждом случае приложение направляет временный локальный порт iPhone/Mac на `127.0.0.1:8766` выбранного узла; публичный HTTP-порт не нужен.

После соединения кнопка **Получить пароль первого входа** запрашивает начальный пароль Hub по тому же проверенному SSH-соединению с выбранного узла. Для конечного узла за ProxyJump используется второе SSH-соединение: выполнение команды не переносится на промежуточный узел. Команда фиксирована: `/usr/bin/cat -- /etc/sovagrid/admin-password`; приложение не подставляет в неё данные профиля и не просит вводить путь или токен в консоли. SSH-пользователь должен иметь право читать этот файл (обычно это `root`, файл создан с правами `0600`). Ответ ограничен по размеру, проверяется код завершения команды; stderr не отображается. Пароль показывается только по кнопке, не сохраняется в Keychain/UserDefaults и удаляется из состояния приложения при закрытии карточки, отключении SSH или уходе в фон. Скопированное значение очищается из буфера обмена не позднее 60 секунд или при отключении, если пользователь не менял его содержимое. На iPhone буфер помечен как локальный; системный буфер Mac может синхронизироваться через Universal Clipboard. После смены пароля в настройках Hub исходный файл остаётся прежним: эта кнопка тогда покажет **устаревший** пароль, который больше не подходит для входа.

Для профиля с ProxyJump приложение отдельно проверяет и закрепляет SSH host key **каждого** узла, используя соответствующий пароль или ключ. Адрес конечного сервера разрешается на промежуточном узле. Если на целевом сервере ещё не установлен Hub либо не открыт его loopback-порт 8766, панель не подключится. Если SSH-соединение или проверка порта зависли, через 30 секунд приложение покажет ошибку и закроет каналы. Закрытие панели завершает локальный слушатель, оба SSH-канала и активные сеансы переадресации.

Панель открывается по временному адресу `http://127.0.0.1:<порт>/sovagrid/monitoring/`. Правило WebKit разрешает только этот локальный источник и блокирует сетевые запросы к другим HTTP(S), WebSocket, FTP и file адресам, включая загрузку ресурсов страницы; если правило не удалось применить, панель не открывается. Ссылки настройки Telegram на BotFather и созданного бота открываются системным приложением после нажатия в главной странице панели; WebView не загружает их сам. Хранилище WebView временное. При уходе с вкладки или переводе приложения в фон локальный слушатель и SSH-туннель закрываются. Если автоматический SSH-вход недоступен, остаётся обычная форма с ролями Hub.

Для защищённого экспорта WireGuard-профиля панель расшифровывает профиль в текущей вкладке и передаёт его нативному приложению через `sovagridNativeProfile`. Приложение принимает сообщение только от главной страницы текущего локального SSH-туннеля, проверяет версию, имя `.conf`, размер и каноническое base64url-кодирование. На iPhone/iPad открывается системное меню «Поделиться» с возможностью «Сохранить в Файлы»; временный файл с защитой данных удаляется после закрытия меню, ухода с панели или перевода приложения в фон. Если приложение было принудительно остановлено, оставшиеся временные файлы удаляются при следующем запуске. На Mac открывается системный диалог сохранения; файл создаётся только после выбора места. Сохранённый профиль содержит приватный ключ VPN-клиента, поэтому храните его в защищённом месте.

## Нативный мониторинг Hub

Вкладка **Мониторинг** напрямую выполняет `POST /api/v1/session`, `GET /api/v1/session`, `GET /api/v1/session/access`, `GET /api/v1/servers`, безопасный `GET /api/v1/servers/{id}/checks`, по запросу наблюдателя `GET /api/v1/servers/{id}/checks/{check_id}/history?limit=60`, два запроса `GET /api/v1/incidents?state=…` и `DELETE /api/v1/session`. Она показывает пользователя и роль, статус сервера, CPU, RAM, диск, load, HTTP/HTTPS/TCP/DNS проверки, историю их запусков и активные/завершённые инциденты. Проверки содержат состояние, последний ответ, задержку, код HTTP и срок действия подтверждённого TLS-сертификата; приложение не запрашивает конфигурацию проверок с адресами целей. История открывается отдельно для выбранной проверки и очищается при смене настроек или выходе из аккаунта. Роль на карточке сервера учитывает его `access_role` и общую роль аккаунта. Оператор или администратор может подтвердить активный инцидент только на сервере с соответствующим правом; запрос `POST /api/v1/incidents/{id}/ack` проверяется Hub повторно. При политике выбранных серверов отсутствие `access_role` скрывает это действие. Старый Hub без `/session/access` использует прежнюю общую роль. Время от Hub разбирается как Unix секунды UTC и отображается по часовому поясу устройства. В подробностях последней метрики доступны показания системных часов, NTP и RTC; `rtc_offset_seconds` подписан как разница RTC и системных часов, а не точность NTP.

Администратор доступного сервера с включёнными командами видит в его карточке нативный раздел **«Службы systemd»**. Он вводит точное имя `.service`, запускает проверку состояния через структурный Hub API и после успешного задания видит только проверенные `load/active/sub` поля. Запуск, остановка и перезапуск доступны после недавней проверки и отдельного подтверждения; перед отправкой клиент повторно проверяет роль, сервер и состояние, а Hub и Agent применяют свои политики независимо. Для SSH, сети, VPN, контейнерного движка, туннелей и SovaGrid нативный клиент оставляет только проверку состояния. Каждый запрос действия получает новый UUID `Idempotency-Key`. Если ответ на изменение потерян, срок ожидания истёк или ожидание отменено после постановки задания, исход считается неопределённым: интерфейс не повторяет команду и требует новую проверку состояния. Старый Hub без поля `remote_commands_enabled` не показывает доступное управление. Нативный клиент не включает локальную политику Agent; её отдельно настраивает администратор хоста.

Там же есть нативный раздел **«Docker-контейнеры»**. Он показывает полный ID, имя, образ и состояние из последнего полного снимка Agent; усечённый список и Podman не открывают действия. Системные контейнеры SovaGrid, Amnezia, SSH, VPN, туннелей и контейнерного движка видны только как состояние инвентаря. Для остальных администратор сначала запускает отдельный `status` job, затем клиент читает точное доказательство через `/containers/control` и предлагает запуск, остановку или перезапуск с подтверждением. Перед каждой отправкой клиент заново получает список серверов и проверяет роль, доступность Agent и точный 64-символьный ID; Hub определяет свежесть снимка по времени получения метрики на своей стороне. После любой попытки изменения, в том числе с потерянным ответом или отменённым ожиданием, повторное действие требует нового `status`. Локальная root-политика Agent для контейнеров по умолчанию выключена и не включается приложением.

При обновлении проверяется identity сессии; изменение пользователя или роли, отключённая учётная запись и некорректные данные пользователя очищают сессию и требуют нового входа. Неизвестная роль отклоняется. Старый Hub без поля `user` поддерживается как система с единственным администратором; отсутствие нового маршрута проверок показывается отдельно и не мешает старому мониторингу. Для удалённого адреса Hub нужен HTTPS; HTTP разрешён только для localhost. Полная панель через SSH доступна на соседней вкладке и не требует внешнего HTTPS-адреса.

Пароли SSH, приватные ключи и закреплённые SSH host keys хранятся в Keychain с классом `WhenUnlockedThisDeviceOnly`. В `UserDefaults` находятся только несекретные поля профиля. Токен прямого подключения к Hub хранится в Keychain, пароль Hub после входа не сохраняется.

Для проверки identity доступны `tests/HubIdentityTests.swift` и `python3 tests/integration/run_hub_identity.py --app <Simulator.app>`. Локальный HTTP-стенд с синтетическими данными проверяет вход наблюдателя, смену id, неизвестную роль и отключение пользователя. Во всех трёх случаях приложение очищает Keychain-сессию и метрики; после перезапуска не отправляет запросы со старым токеном. Сценарий использует только синтетические данные.

Для мониторинга 0.5 доступны `tests/HubMonitoringTests.swift` и `python3 tests/integration/run_hub_monitoring.py --app <Simulator.app>`. Отдельный Simulator входит наблюдателем в локальный Hub-стенд, отображает HTTP/HTTPS/TCP сводки, активный и завершённый инциденты и разницу RTC с системными часами. Стенд добавляет секретный адрес цели как лишнее поле ответа и проверяет, что клиент его не показывает и не вызывает административный `/checks/config`. Тест не подключается к рабочим серверам.

Для нативных служб доступны `tests/HubServiceTests.swift` и `python3 tests/integration/run_hub_services.py --app <Simulator.app>`. Тестовая машина входит как синтетический администратор, проверяет `nginx.service`, подтверждает один фиктивный перезапуск и проверяет запрос нового статуса перед следующим действием. Реальные службы и серверы не затрагиваются.

Для Docker доступны `tests/HubContainerTests.swift` и `python3 tests/integration/run_hub_containers.py --app <Simulator.app>`. Сквозной тест использует локальный синтетический Hub, где снимок контейнеров на 28 секунд старше общей метрики, проверяет точный ID и порядок `status → control → подтверждение → restart`, а затем отсутствие возможности повторить изменение без нового статуса. Сборку для Simulator нужно подписать локально (`CODE_SIGNING_ALLOWED=YES CODE_SIGN_IDENTITY=-`), иначе Keychain может отказать в сохранении Hub-сессии с ошибкой `-34018`. Отдельный `python3 tests/integration/run_live_hub_readonly.py --app <Simulator.app> --hub <https-origin> --ssh-host <authorized-host>` проверяет реальный HTTPS-вход, список серверов и защиту системного Docker-контейнера только в режиме чтения. В мобильном списке серверы расположены перед историей завершённых инцидентов, чтобы длинная история не скрывала переход к ним.

На карточке сервера доступен нативный раздел «Диски и тревоги». Он читает отдельный `GET /api/v1/servers/{id}/filesystems/alerts` и показывает свежесть источника, использование места и inode по точкам монтирования, действующие пороги и состояние измерений. Администратор может добавить правило только из свежего полного списка, изменить порог, задержку срабатывания или удалить правило; `PUT` использует точную ревизию и подтверждение. При потерянном ответе новый `PUT` не повторяется: сначала обновите состояние. Наблюдатель видит правила без кнопок изменения. Инциденты сертификатов, контейнеров и отдельных файловых систем имеют собственные подписи в списке событий. Это изменение исходников не создаёт отдельный релиз приложения.

## Проверка

На iPhone Simulator локальные SSH-стенды проверяют команды, ProxyJump, независимую проверку ключей двух узлов и закрытие туннеля. [Web-панель Hub](screenshots/ios-panel-over-ssh.png) загрузила форму входа через SSH-переадресацию; [локальный стенд](screenshots/ios-hardened-panel-local-fixture.png) отдельно проверил правила WebKit. Физическое устройство проверяется отдельно перед публикацией бинарного клиента.

Нативный обработчик экспорта профиля собран для iOS Simulator и macOS. Отдельные тесты проверяют допустимые размеры и отклонение неверного JSON, имени файла и base64url. На iPhone 18 Pro Simulator проверен путь через локальный SSH-туннель и WKWebView: сообщение из вложенного фрейма не открыло меню, сообщение из главной страницы открыло [системное меню с файлом `.conf` и действием «Сохранить в Файлы»](screenshots/ios-profile-share-fixture.png). Временный файл имел права `0600` и исчез при переводе приложения в фон; файлы от принудительного завершения удалились при следующем запуске. Проверка использовала синтетический файл из четырёх байтов; экран сохранения с реальным профилем на физическом устройстве пока не проверен.

Разбор ссылок Telegram проверен отдельным тестом: допускаются `https://t.me/BotFather` и прямой адрес бота, а поддельный домен, порт, параметры, вложенный путь и другие внешние ссылки отклоняются. Изменение собрано для iOS Simulator и macOS; фактическое открытие Telegram на физическом устройстве пока не проверено.

Разбор ответа для пароля первого входа проверен отдельным тестом на допустимый однострочный пароль, управляющие символы и превышение размера. Версии iOS Simulator и macOS собраны. Получение реального пароля по SSH и вставка в форму на физическом iPhone пока не проверены.

Маршруты панели для профиля с ProxyJump проверены тестом выбора узла и сборками iOS Simulator/macOS. Локальный iPhone Simulator UI-тест открыл WKWebView через промежуточный и конечный узлы и прочитал два разных синтетических пароля. В воспроизводимом сценарии [`tests/integration/run_panel_routes.py`](tests/integration/run_panel_routes.py) промежуточный SSH-сервер блокирует прямое соединение с портом панели конечного узла, поэтому второй маршрут проходит только через отдельное SSH-соединение. Сценарий создаёт отдельный Simulator и локальные SSH/HTTP стенды на `127.0.0.1`.

Для файлов отдельно проверены сборки iOS Simulator/macOS, двоичная загрузка и скачивание против системного `sftp-server` macOS, права `0600` и отказ перезаписывать существующий файл. `python3 tests/integration/run_panel_routes.py --sftp-only` проверяет iPhone Simulator с двумя SSH-серверами: сохранённый профиль проходит через ProxyJump, скачивает двоичный файл 30006 байт без изменений и открывает [системное действие Save to Files](screenshots/ios-sftp-save-fixture.png). Системный выбор показан в симуляторе; запись файла в выбранную папку и загрузка через системный picker на физическом устройстве ещё не проверены. Импорт ключей этого формата доступен через системный выбор файла.


Для импорта отдельно проверены ключ, созданный системным `ssh-keygen`, совпадение открытой части, отклонение зашифрованного, повреждённого и слишком большого файла, а также несогласованной бинарной структуры. iPhone Simulator UI-тест открыл офлайн-лицензию и выбор импорта для конечного и промежуточного серверов. Сборки iOS и macOS содержат копии лицензий зависимостей. Для проверки на собственном одноразовом Ubuntu-стенде доступна команда `python3 tests/integration/run_key_import.py --server <host> --app <Simulator.app>`; она создаёт помеченную временную учётную запись без sudo и не передаёт административный ключ в приложение.

## Текущие ограничения

SwiftNIO SSH 0.13.0 поддерживает здесь пароль и Ed25519. Импорт ключей с парольной фразой, вход с RSA user key, keyboard-interactive/OTP и автоматическое восстановление сессии пока не реализованы. Файловый клиент поддерживает только SFTP v3 и операции просмотра папок, загрузки и скачивания файлов. В Web-панели ограничения WebKit защищают загрузки через известные сетевые схемы; аудит браузерного движка и стороннего Web-контента перед публичным выпуском остаётся необходимым. Если закреплённый SSH host key изменился, профиль нужно удалить и добавить заново только после независимой проверки нового отпечатка.

Зависимости: [SwiftNIO SSH 0.13.0](https://github.com/apple/swift-nio-ssh), [SwiftTerm 1.11.2](https://github.com/migueldeicaza/SwiftTerm), [Swift Crypto](https://github.com/apple/swift-crypto). Версия SwiftTerm 1.20.0 требовала отсутствующий в этой установке Xcode Metal Toolchain; 1.11.2 удалось собрать для обеих платформ.
